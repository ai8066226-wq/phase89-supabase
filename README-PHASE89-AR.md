# آمرني — Phase 89 — تأمين العمليات الحساسة على Supabase

هذه المرحلة تنقل العمليات المالية وحالات الطلب الحساسة من المتصفح إلى PostgreSQL RPC محمية داخل Supabase.

## ما تم تأمينه
- إنشاء طلبات التكسي والتوصيل وخصم رسم العميل داخل معاملة سيرفرية واحدة.
- قبول الكابتن وخصم رسمه وحجز `activeOrderId` بصورة ذرية.
- انتقال حالات الرحلة والتحقق من OTP ورمز استلام المطعم على السيرفر.
- الإكمال التلقائي عبر GPS يتحقق من دقة وحداثة وموقع الطرفين داخل قاعدة البيانات.
- إنشاء طلبات الخدمات وقبول مزود الخدمة ورسومه ونشر النشاط ورسوم النشر على السيرفر.
- إنشاء طلبات الشحن ومراجعتها من الإدارة وإضافة الرصيد مع سجل `walletTransactions`.
- إلغاء العميل/الكابتن/مزود الخدمة يحرر حجز الكابتن المرتبط عند الحاجة.
- منع المستخدم من تعديل `role` أو `balance` أو الرصيد المجاني أو حقول الرسوم مباشرة.
- صلاحيات Data API أصبحت صريحة: الزائر يقرأ البيانات العامة فقط، والمستخدم المسجل يخضع لـ RLS.

## البنية الحالية
- Auth: Supabase Auth + Edge Functions `public-signup` و`delete-self`.
- Data/Reatime: `karwa_documents` كجسر توافق مؤقت مع منطق Firestore القديم.
- Storage: Supabase Storage (`service-assets` و`driver-documents`).
- Push: ملف FCM القديم باقٍ للإشعارات فقط، وليس قاعدة بيانات أو Auth أو Storage.

## ملاحظة انتقالية
ما زال `supabase-compat.js` يحافظ على API شبيه Firestore لتقليل كسر الواجهات. المرحلة التالية المناسبة هي ترحيل البيانات التاريخية من Firebase ثم تحويل الوحدات تدريجيًا من جسر JSON إلى الجداول العلائقية الأصلية في Supabase.
